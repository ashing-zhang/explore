  \---

  需求转化率的准确定义

  在这个系统语境里，需求转化率 ≠ 入住率，它是：

  ▎ 在价格 P、市场状态 S 下，一个潜在客户看到这个房源后实际完成预订的概率

  更准确的分解：

  实际销量 = 曝光量 × 需求转化率 × min(1, 库存/需求)

​                ↑           ↑                ↑

​             有多少人看到   价格驱动的意愿    库存是否够

  \---

  为什么不直接用销量

  你的直觉是对的——目标确实是"理解价格变化带来的销量变化"。但直接用销量会把三件事混在一起：

  ┌───────────────────────┬────────────────────────────┐

  │      你想隔离的       │     混入销量的其他噪音     │

  ├───────────────────────┼────────────────────────────┤

  │ 价格 → 需求的真实响应 │ 曝光量变化（平台调整排位） │

  ├───────────────────────┼────────────────────────────┤

  │                       │ 库存约束（没房可卖）       │

  ├───────────────────────┼────────────────────────────┤

  │                       │ 季节基础水位               │

  └───────────────────────┴────────────────────────────┘

  举例： 五一你卖出了 8 间房，是：

  \- 需求旺、但库存只有 8 间？（真实需求可能 50 间）

  \- 还是需求本来就弱，只有 8 个人想买？

  这两种情况价格策略完全相反。用销量你无法区分，用需求转化率可以——因为它在分母上把库存约束给"剥离"了。

  \---

  为什么必须考虑库存

  这直接来自 need.md 里引用的那篇 2026 年论文的核心公式：

  成交量 B ≤ min(真实需求 D, 库存供给 S)

  当库存 < 真实需求时（供给约束），销量被截断了——你观测到的不是真实需求，是库存上限。如果拿这个数据去拟合弹性模型：

  你训练出来的模型以为：价格 P 时需求 = 8（实际是 50）

  → 弹性系数被严重低估

  → 系统认为需求对价格不敏感

  → 给出错误的"可以降价"建议

  论文里说的："忽略供给限制，会导致模型学到一个被截断的世界"，就是这个意思。

  \---

  概念关系总结

  需求转化率（本系统建模的目标）

​      ↓ × 曝光量（排位决定）

  真实需求

​      ↓ 遇到库存天花板后

  实际销量（你账上记录的那个数）

  所以需求转化率是中间层：比销量"纯"（剥离了库存截断和曝光噪音），比"有没有人想买"更具体（可以和价格建立函数关系）。库存

  不是用来建模弹性的，而是用来修正训练数据里的偏差，防止系统学到一个失真的世界。

最后这句啥意思，如果我们作为平台方，先拿销量/库存的平台库存消化率来当作需求转化率可不可以？

● 这是个很实际的好问题。可以用，但有一个致命盲区需要知道。

  \---

  先说为什么可以

  当你的库存没卖完时：

  库存消化率 = 销量 / 持有库存

​             = 真实需求 / 持有库存   ← 此时两者相等

  这时需求没有被库存截断，消化率就是真实的需求响应信号。这段数据可以直接用来拟合弹性曲线，是干净的。

  \---

  致命盲区：消化率打满的时候

  当消化率 = 100%，你只知道真实需求 ≥ 库存，但不知道多出来多少：

  消化率 100%，持有10间 → 真实需求可能是 10、30、100

  这三种情况价格策略完全不同：

  ┌──────────┬────────────────────┬─────────────────┐

  │ 真实需求 │      信号含义      │   应该做什么    │

  ├──────────┼────────────────────┼─────────────────┤

  │ 刚好 10  │ 价格在均衡点       │ 维持价格        │

  ├──────────┼────────────────────┼─────────────────┤

  │ 30       │ 价格偏低，大量溢出 │ 大幅提价        │

  ├──────────┼────────────────────┼─────────────────┤

  │ 100      │ 严重供不应求       │ 极限提价 + 补货 │

  └──────────┴────────────────────┴─────────────────┘

  但你拿到的数据都是一样的：销量=10，消化率=100%。

  用这批数据拟合弹性曲线，模型会以为"这个价格下需求 = 10"，严重低估真实需求，导致弹性系数失真，给出错误的定价建议。这就是"学到一个被截断的世界"的具体含义。

  \---

  实际操作建议

  不是要放弃库存消化率，而是要分开处理：

  消化率 < 90%  → 干净数据，直接用，可信的弹性信号

  消化率 ≥ 90%  → 截断数据，只能告诉你"需求至少这么高"

​                   拟合模型时要特殊处理，不能当普通观测值用

  统计学上这叫 Tobit 模型（截断回归），专门处理这类"只知道下界"的观测值。

  \---

  还有一个分母的问题

  用库存消化率时，分母的"库存"必须是你挂出来的库存，不是持有总量，也不是酒店总房量。

  如果你持有 20 间但只挂出 5 间，5 间全卖完，消化率 = 100%——但这反映的是你自己的挂单策略，不是市场需求。真实需求可能只有 5 个人，也可能有 50

  个人在搜但没看到你的房源。

  \---

  结论

  库存消化率是一个务实的起点，平台方用它完全合理，比直接用销量已经好很多。核心是要在两个地方做对：

1. 消化率打满的数据点，拟合时当"下界约束"处理，而不是精确观测值

2. 分母用挂单量，不是持仓量
